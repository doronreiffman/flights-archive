# Data model: raw snapshots to observations and flights

Grade: production-lean. A deterministic full rebuild with tested rules, runnable on a laptop now and in a small Lambda later. No incremental processing yet; the trigger for adding it is the nightly rebuild passing about five minutes (see "Nightly run").

## Inputs

`data/raw/` and `data/receipts/` are copies of the bucket's `raw/` and `receipts/` prefixes, made by `sh scripts/sync.sh` (read-only; receipts first, then raw; the folder is gitignored). Each snapshot is one or more files `date=YYYY-MM-DD/HHMMSSZ-<sha12>/page-NNN.json.gz`, the untouched CKAN `datastore_search` reply. The fetch time comes from the path (to the second, UTC). The resource's own `last_modified` is only in the S3 object metadata, which a sync does not keep; the model uses fetch time as the observation time, which is 25 s to 2 min later than the board refresh. Every archived snapshot has rows: the collector refuses a zero-row reply, so an empty board never reaches the archive. A snapshot whose files hold fewer rows than the reply's own `total` (a multi-page store interrupted after the first page) is dropped and listed in `snapshot_runs` as incomplete.

Receipts (`docs/receipts.md`) decide which snapshots the model trusts. Each snapshot gets a status in `snapshot_runs.receipt`: `receipted` (a stored receipt names it and its row and page counts match the files) and `legacy` (no receipt, fetched before the first receipt in the archive; judged by the declared `total` as before) are kept; `orphan` (no receipt, listed in `KNOWN_ORPHANS` in `rules.py` after a person checked S3), `superseded` (no receipt, and the next snapshot holds the same content with a receipt: a failed receipt write, stored again by the next run) and `pending` (newer than every local receipt) are dropped. The build stops, naming the snapshots, on anything else: a snapshot with no receipt between receipts, a pending snapshot more than `PENDING_GRACE_MINUTES` (35) after the newest receipt (receipts synced earlier than raw, or receipt writes failing), a receipt whose counts differ from its files, a receipt whose snapshot has no files, or a receipt version this model does not know. Silently dropping any of these could move a flight's first CANCELED sighting by a refresh without a flag. With no receipts at all, every snapshot is `legacy`.

## Outputs (Parquet, in `data/model/`)

- `receipts.parquet`: one row per acquisition receipt, stored or unchanged: run start and download times, the board's `last_modified`, the snapshot it names, rows, pages, code fingerprint.
- `snapshot_runs.parquet`: every snapshot found, with its receipt status, `incomplete`, `repeat` and `identical_repeats`.
- `snapshots.parquet`: one row per snapshot. id, fetched_at, pages, rows, duplicate rows removed, key conflicts, board window (min and max scheduled time).
- `observations.parquet`: one row per flight per change. Every field of the board row, local times kept and UTC times added with their DST flags, the snapshot it came from, `change_kind` (`first`, `change`, `retime`) and `changed_fields` (which fields differ from the previous observation of the same flight).
- `flights.parquet`: one row per marketed flight, that is one airline and flight number on the board, with its retimes linked into one row. The physical movement (the aircraft) is the codeshare group that R5 infers, so several `flights` rows usually share one `codeshare_group_id`; the feed names no operator, and R6's guess stays marked as a guess. Identity, first/last seen, scheduled times (first and final, local and UTC), retime count, first and final status, outcome, first time seen CANCELED with the lead time and a censoring flag, codeshare group and size, operating-carrier guess.

## Rules

Each rule is a named SQL step in `src/model/rules.py` with its own tests. UNSURE marks a choice the data does not settle; it is applied consistently and flagged in the output rather than hidden.

- **R1 Time conversion.** Board times are Israel wall-clock with no offset. For each one, try both candidate offsets (UTC+2 and UTC+3) and keep the one that converts back to the same wall-clock. Both valid means the fall-back hour (01:00–01:59 on the last Sunday of October): take the earlier instant (UTC+3) and set `*_ambiguous`. Neither valid means the spring-forward gap (02:00–02:59 on the Friday before the last Sunday of March): shift forward an hour and set `*_nonexistent`. UNSURE: the earlier-instant choice for the repeated hour; nothing in the feed says which occurrence the board means. Two hours a year are affected (one repeated in October, one missing in March); the review brute-forced the macros against Python's zoneinfo every 10 minutes from 2025 to 2027 with no mismatch.
- **R2 Duplicate removal.** A snapshot whose content hash (the sha12 in its path) equals the previous kept snapshot's (snapshots dropped for their receipt status do not count) is the same board stored twice (the collector's snapshot write succeeded but its state write failed, or a receipt write landed but reported an error); it is dropped and counted on the kept snapshot as `identical_repeats`. Within one snapshot, rows identical on all 17 fields collapse to one; the count goes to `snapshots.duplicate_rows`. Rows that share the board key (airline, flight number, direction, airport, scheduled time) but differ elsewhere keep the lowest `_id` and count as `key_conflicts`. UNSURE: no key conflict has been seen yet, so the lowest-`_id` choice is untested against reality.
- **R3 Change detection.** Per board key, compare the row with the key's previous appearance. A difference in any field emits an observation with the changed field names; the first appearance emits `first`. Unchanged appearances emit nothing; `flights.last_seen_at` still records them.
- **R4 Retime linking.** A key that leaves the board while its status is not terminal (DEPARTED, LANDED, CANCELED) links to a key with the same airline, flight number, direction and airport that first appears in the very next snapshot with a scheduled time within 12 h of the old one and a non-terminal status. Nearest scheduled time wins; ties and many-to-one matches stay unlinked and are counted. The chain's first key is the physical flight's id; the linked key's first observation is `change_kind = 'retime'`. A link is never made across a collection hole (next snapshot more than `GAP_HOURS` = 1 h after the old key's last appearance). UNSURE: the 12 h window (chosen so the next day's same flight number cannot link); the next-snapshot strictness; and the overlap case: if the board ever shows the old and the new row in the same refresh, R4 does not link them and the old key ends as `vanished`, which is the project's headline signal. The report counts vanished flights that shared the board with a same-number flight within 12 h so this can be checked once real retimes exist.
- **R5 Codeshare grouping.** Within one snapshot, rows with the same direction, airport, scheduled time, estimated time, terminal and counters are one physical movement. A flight's group is the group it sat in at its last appearance; the group id is a hash of its members' flight ids there. `codeshare_basis` is `counters` when counters are non-empty and `time-only` otherwise (all arrivals). UNSURE: `time-only` groups can merge two real flights from the same airport at the same scheduled and estimated minute; the estimated time in the key is what splits them when the board knows better (EY 596 and EY 610 to AUH, 07:00, counters 12-21, estimates 07:18 and 08:24, split correctly). A partner that leaves the board at a different snapshot can land in a different group id.
- **R6 Operating-carrier guess.** In a group, the member with the lowest numeric part of its flight number; ties go to the alphabetically first airline code. A group of one is its own operator. `operating_is_guess` is true whenever the group has more than one member. UNSURE: pure convention (marketing codeshare numbers are usually high, four digits); nothing in the feed names the operator.
- **R7 Final status and outcome.** `final_status` is the last observed status. `outcome` is `departed`, `landed` or `canceled` when the final status is terminal; `open` when the flight is still on the latest snapshot; `vanished` when it left the board with a non-terminal status, no retime link and a scheduled time more than 1 h after its last appearance (a possible unflagged cancellation); `dropped` otherwise (rolled off the board after its time with a non-terminal status). UNSURE: the 1 h threshold.
- **R8 Cancellation lead time.** The announcement is bracketed, not pinned: it came after `cancel_announced_after` (the flight's last appearance that was not CANCELED) and by `canceled_first_seen_at` (the first observation with status CANCELED). `cancel_lead_min` is the scheduled UTC time at that first CANCELED observation minus `canceled_first_seen_at` (a lower bound on how far ahead it was announced); `cancel_lead_max_min` is the same from `cancel_announced_after` (an upper bound); `cancel_bracket_min` is their difference, one board refresh with continuous collection. `cancel_lead_censored` is true when the bracket is only a bound: the flight was already CANCELED when first seen (`canceled_at_first_sight`, the real announcement was earlier, possibly before the flight entered the 72 h window) or the bracket spans a collection hole (then the scheduled time may even sit inside it and `cancel_lead_min` goes negative). Statistics use only uncensored flights. `uncanceled` is true when a later observation has another status.

## Tests

Synthetic snapshots (small CKAN replies written in the raw layout to a temp folder) exercise each rule in isolation: normal, ambiguous and nonexistent local times; exact duplicates and key conflicts; change detection on each field; retime positive, 12 h boundary, terminal-status exclusion, next-day same number, ties; codeshare groups with and without counters, split by estimated time; operating guess with padded and lettered flight numbers; each outcome; cancellation lead time, censoring and uncancel. One test runs the whole pipeline on the real 38-row fixture. Mutation check: each rule is broken on purpose once to see its test fail.

## Nightly run (proposal, not deployed)

Measured first (this Mac, synthetic copies of the real snapshots 15 min apart, a pessimistic workload because the copies change every refresh):

| snapshots | raw rows | wall time | peak memory |
|---|---|---|---|
| 150 (1.5 days) | 0.3 M | 3.5 s | 1.0 GB |
| 600 (6 days) | 1.2 M | 13 s | 1.5 GB |

The full rebuild is fine on a laptop for months, and it is what the model does today. It is not a nightly Lambda: memory grows with the whole history, so a 2 GB function would run out after about two weeks of snapshots, and reading every raw file every night makes S3 requests grow linearly (35,000 a night by month twelve). The proposal is therefore in two steps, and only the second one creates infrastructure:

1. **Make the build incremental** (code only, next piece of work). Stage one appends each night's new raw files to a date-partitioned `rows/` Parquet, idempotent by snapshot id. Stage two rebuilds observations and flights only for the trailing window of flights that can still change (a flight lives on the board at most about five days, so roughly ten days of rows) and keeps closed flights as they are. Nightly work is then about 100 files and a few hundred thousand rows whatever the history's size.
2. **Then a second Lambda in the same stack**, `ModelFunction`: Python 3.13 with the `duckdb` wheel bundled (20 MB zipped for arm64, inside the 50 MB limit), 2048 MB memory, 10 min timeout, 2 GB ephemeral storage with DuckDB's `temp_directory` and `memory_limit` pointed at it (its default temp directory is relative to the working directory, which is read-only in Lambda), EventBridge Scheduler daily at 01:30Z, no retries. It reads `raw/` through DuckDB's httpfs extension (the build needs an S3 glob, not a local path, so `build.py` grows an option for it) and writes `rows/` and `model/` to the archive bucket. Those keys get no Object Lock retention (the bucket only locks what the collector locks explicitly), so each night overwrites `model/`; a lifecycle rule expires non-current versions after 7 days. A healthchecks.io check with a daily period and the existing SNS alarm cover failures.

Cost of step 2, per month: Lambda 2 GB × about 1 min × 30 nights = 3,600 GB-s, inside the 400,000 GB-s free tier, so $0. S3: about 100 GETs and a handful of PUTs a night, under $0.01; storage for `rows/` and `model/` reaches about 1 GB a year, $0.02. Total under $0.05 a month, and flat. Alternative considered: a nightly GitHub Actions job (free on a public repo) writing through an OIDC role; rejected for now because it adds a cross-account trust to the one account that holds the data.

## How to run

```bash
sh scripts/sync.sh   # checks the AWS identity, then syncs receipts/ and raw/ into data/, in that order
PYTHONPATH=src .venv/bin/python -m model.build --raw data/raw --out data/model
PYTHONPATH=src .venv/bin/python -m model.report --model data/model > docs/data-quality-YYYY-MM-DD.md
.venv/bin/python scripts/mutation_check.py   # breaks each rule in turn; every break must fail a test
```

## Columns

`snapshot_runs`: every snapshot file set found, with `incomplete`, `receipt` (receipted, legacy, orphan, superseded, pending), `repeat` and `identical_repeats`; the ones kept become `snapshots`.

`receipts`: receipt_file, receipt_version, action, run_started_at, downloaded_at, resource_last_modified, snapshot_id, snapshot_sha256, rows, pages, code_sha256. Times are naive UTC.

`snapshots`: snapshot_id, fetched_at, snap_rn (1-based order), gap_before_s, pages, rows_raw, rows (after R2), duplicate_rows, key_conflicts, unparsed_sched, missing_est, identical_repeats, min_sched_local, max_sched_local.

`observations`: flight_id, key_id, snapshot_id, snap_rn, observed_at, prev_observed_at, change_kind, changed_fields, then the board row under plain names (airline, flight_no, airline_name, direction, airport, airport_name, city_en, city_he, country_en, country_he, sched_local, sched_utc, sched_ambiguous, sched_nonexistent, est_local, est_utc, est_ambiguous, est_nonexistent, terminal, counters, zone, status, status_he). The board field for each name is in `COLUMNS` in `src/model/rules.py`; the datastore's own notes label the city pair the wrong way round, and the mapping follows the data.

`flights`: flight_id, identity (airline, flight_no, airline_name, direction, airport, airport_name, city and country names), sched_local_first, sched_local_final, sched_utc_final with DST flags, retimes, key_ids, first_seen_at, last_seen_at, snapshots_seen, observations, first_status, final_status, final_status_he, outcome, est_local_final, est_utc_final, est_minus_sched_min, terminal_final, counters_final, zone_final, canceled_first_seen_at, cancel_announced_after, cancel_lead_min, cancel_lead_max_min, cancel_bracket_min, canceled_at_first_sight, cancel_lead_censored, uncanceled, codeshare_group_id, codeshare_size, codeshare_basis, operating_airline, operating_flight_no, operating_is_guess.

## Deviations

- **Collection gaps get their own outcome.** The first real build called 351 flights `vanished` and gave negative cancellation lead times, all because nothing was collected between 2026-10-27 18:24Z and 2026-10-29 12:29Z. New rule: when the snapshot after a flight's last appearance came more than `GAP_HOURS` (1 h) later, the outcome is `gap` (fate unknown) and R4 refuses to link a retime across it. The 8 retime links the first build found all straddled that hole and are gone; none has happened inside the continuous run yet.
- **Cancellation announcement is a bracket, not a point.** R8 now records `cancel_announced_after` (the last appearance that was not CANCELED) beside `canceled_first_seen_at`, and both `cancel_lead_min` (lower bound, from the first CANCELED sighting) and `cancel_lead_max_min` (upper bound, from the appearance before). With continuous collection the bracket is one board refresh wide.
- **No duplicate rows yet.** The 61 earlier snapshots had them (LY 9951); the 6 archived ones do not, so R2's duplicate path is proven only by tests.
- **After the independent review (2026-10-29).** DuckDB's `arg_max` skips NULL values, so a flight whose last observation blanked the estimated time kept the earlier estimate and reported a made-up delay; the first and final states now travel as structs. The nightly-run section was rewritten around measured numbers; the first draft budgeted "2 GB × 2 min" from guesswork. R8 gained `cancel_bracket_min` and `cancel_lead_censored` (the real build had eight cancellations whose bracket spanned the 42 h hole, with negative lead times and no flag). The report now carries the data.gov.il / IAA attribution line. Key ids coalesce NULL fields, key_ids follow chain order, and a dead window sort over all 17 fields was removed. Twelve tests and ten mutations were added for the branches the review found untested (old key seen several times, many-to-one links, the window's negative side, terminal in the codeshare key, the airline tie-break, the 1 h horizon, the gap measured from the last appearance, two-page snapshots, a hole in a flight's appearances, a NULL estimate last).
